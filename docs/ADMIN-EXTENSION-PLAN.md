# แผนเพิ่มบัญชีส่วนตัวและระบบจัดการส่วนกลาง

วันที่ 8 พฤศจิกายน 2569 · ตรวจจากโค้ดและ CONTRACT v0.3.3 · ผู้ใช้อนุมัติแล้วและดำเนินการส่วนเพิ่ม พร้อมตรวจรับ A5 ดู ADMIN-REVIEW.md และ evidence/management-summary.json

ผู้ใช้รับกระบวนการเดิมที่ G2 และแจ้งว่าส่วนจัดการยังไม่สมบูรณ์ จากนั้นเลือก **บัญชีแอดมินเฉพาะ** และอนุมัติแผนพร้อมขอให้ลดความยากในการเดินงาน รายการด้านล่างเป็นขอบเขตที่นำมาดำเนินการ ดูผลจริงใน ADMIN-REVIEW.md และ MANAGEMENT-TRACEABILITY.md

## ข้อค้นพบจากระบบจริง

| ส่วน | มีอยู่แล้ว | ช่องว่าง |
|---|---|---|
| พนักงาน | login/logout, bcrypt, session, role/craft, is_active | ไม่มีหน้าบัญชีส่วนตัว เปลี่ยนรหัสผ่าน จัดการพนักงาน หรือออกบัญชีใหม่ |
| บ้าน | UC-01 สร้างบ้านและตรวจเลขซ้ำ, เลือกบ้าน, เปลี่ยนสถานะตาม workflow | ไม่มีทะเบียนบ้านส่วนกลาง ค้นหาแบบครบ แก้ข้อมูลพื้นฐาน หรือเก็บเข้าคลัง |
| ลูกค้า | ค้นจากเลขประจำตัวตอนผูกบ้าน สร้าง/ผูกลูกค้า ออกลิงก์ | ไม่มีทะเบียนลูกค้า แก้ข้อมูลติดต่อ หรือจัดการลิงก์ทั้งหมด |
| โครงการ | project_name เป็นข้อความใน property_unit | ไม่มีทะเบียนโครงการแยก การเปลี่ยนชื่อยังไม่มีแนวทางจัดการประวัติ |
| ผู้ดูแล | ไม่มี ADMIN ใน role, ไม่มี admin route/service | ยังไม่มีบัญชี/เมนู/สิทธิ์ผู้ดูแลระบบ |
| ประวัติ | มีวันที่และผู้ทำบางขั้นของ workflow | ไม่มีบันทึกการแก้ข้อมูลส่วนกลาง/สิทธิ์/บัญชีอย่างต่อเนื่อง |

หลักฐาน: `src/server/auth.ts`, `src/server/workflows.ts`, `src/server/workspace.ts`, `src/lib/runtime-contracts.ts`, `src/app/api/[...path]/route.ts`, `db/001-p1-candidate.sql` และ CONTRACT ส่วน GAP-12 ซึ่งกำหนดให้ employee เป็น seed และไม่มี UC สร้างพนักงาน

ดังนั้นคำว่า “ครบ 18 UC” ในผล G2 หมายถึงกระบวนการธุรกิจเดิม ส่วนการดูแลระบบยังต้องเพิ่มเพื่อให้ใช้งานต่อเนื่องได้

## ขอบเขตที่เสนอ

| โมดูล | ความสามารถ | ข้อกำหนดสิทธิ์/ประวัติ |
|---|---|---|
| บัญชีของฉัน | ดู/แก้ชื่อและข้อมูลติดต่อที่อนุญาต เปลี่ยนรหัสผ่าน ดูรายการเข้าสู่ระบบ/ออกจากระบบอื่น | แก้ role/craft/สถานะบัญชีตนเองไม่ได้ เปลี่ยนรหัสต้องยืนยันรหัสเดิมและเพิกถอน session เดิม |
| ข้อมูลลูกค้าผ่านลิงก์ | ดูข้อมูลบ้าน/ตนเอง แก้ข้อมูลติดต่อที่อนุญาต | คงการใช้ลิงก์เดิม ชื่อทางสัญญาและเลขประจำตัวให้ผู้มีสิทธิ์ตรวจแก้พร้อมเหตุผล ไม่สร้างรหัสผ่านลูกค้าโดยอัตโนมัติ |
| พนักงานและสิทธิ์ | ค้นหา เพิ่มบัญชี แก้ข้อมูล กำหนดฝ่ายขาย/ฝ่ายตรวจ/ช่าง/หัวหน้าช่างและประเภทงาน เปิด/ปิดบัญชี รีเซ็ตรหัสผ่าน | ใช้รหัสชั่วคราวที่ต้องเปลี่ยน ไม่แสดงรหัสเดิม เพิกถอน session เมื่อปิด/รีเซ็ต/เปลี่ยนสิทธิ์ รักษาประวัติงานของบัญชีเดิม |
| โครงการและบ้าน | ทะเบียน ค้นหา กรอง เรียงลำดับ แบ่งหน้า เพิ่ม/แก้ข้อมูลพื้นฐาน เก็บเข้าคลัง/นำกลับ ดูประวัติ QC/คำขอ/ซ่อม/ส่งมอบ | แยก “แก้ข้อมูลบ้าน” จาก “เปลี่ยนสถานะงาน” ไม่ใช้ admin ข้ามผลตรวจหรือการยอมรับของลูกค้า |
| ลูกค้าและบ้านที่ผูก | ทะเบียน ค้นหา/แก้ข้อมูลที่อนุญาต ดูบ้าน/คำขอ/นัด/เอกสารที่เกี่ยวข้อง | แก้การผูกบ้านได้เฉพาะก่อนเริ่มการตรวจลูกค้าและต้องมีเหตุผล พร้อมเพิกถอนลิงก์/session เดิม; หลังเริ่มตรวจให้คงประวัติและเข้าสู่กรณีแก้ไขเฉพาะ ไม่เปลี่ยน FK เงียบ ๆ |
| ลิงก์และการเข้าสู่ระบบ | ออกลิงก์ใหม่ ดูวันหมดอายุ เพิกถอนลิงก์/การเข้าสู่ระบบ | ไม่แสดง token เดิมจากฐานข้อมูล การเพิกถอนมีผลต่อ session ลูกค้าทันที |
| ภาพรวมงาน | จำนวนบ้านแต่ละสถานะ งานค้าง นัดใกล้ถึง และทางเข้ารายการที่เกี่ยวข้อง | คำนวณจากข้อมูลจริง กดไปถึงต้นทางได้ มีสถานะไม่มีข้อมูล |
| ประวัติการจัดการ | ใคร ทำอะไร กับรายการใด เมื่อไร เหตุผล และค่าที่เปลี่ยนตามรายการที่อนุญาต | ไม่บันทึกรหัสผ่าน/token หรือเลขประจำตัวเต็มใน log; บันทึกการเปลี่ยนแปลงสำเร็จใน transaction เดียวกับข้อมูล |

เมนูแอดมินที่เสนอ: **ภาพรวม / โครงการ / บ้าน / ลูกค้า / พนักงาน / ลิงก์และการเข้าสู่ระบบ / ประวัติการจัดการ / บัญชีของฉัน**

บัญชี ADMIN เป็นสิทธิ์ส่วนจัดการโดยเฉพาะ ไม่ได้รับสิทธิ์อนุมัติ QC รับงานช่าง หรือเซ็นแทนลูกค้าจากการเป็นแอดมิน หัวหน้าช่างไม่กลายเป็นแอดมินโดยอัตโนมัติ

## WBS และลำดับงาน

| เฟส | งาน/ผลที่ตรวจได้ | Dependency และ milestone |
|---|---|---|
| A0: ล็อกส่วนต่อขยาย | รายการสิทธิ์ ข้อมูลที่แก้ได้ กฎ archive/reset/rebind และ migration/backfill plan | ใช้ข้อเลือกบัญชีแอดมินเฉพาะที่ยืนยันแล้ว; ตรวจทานขอบเขตนี้ก่อนเปลี่ยนฐานข้อมูล |
| A1: สิทธิ์และความรับผิดชอบ | เพิ่ม ADMIN ใน runtime, สร้างบัญชีแรกตามข้อมูลที่ผู้ใช้กำหนด, session guards, audit, backup/migration | ต้องเสร็จก่อนเปิดการเขียนข้อมูลส่วนกลาง; checkpoint ตรวจ login/denial/rollback |
| A2: บัญชีส่วนตัวและพนักงาน | โปรไฟล์ เปลี่ยนรหัส รีเซ็ต สร้าง/ปิดบัญชี เปลี่ยนประเภทช่าง | พึ่ง A1; ทำ UI และ service/tests คู่กันได้หลังล็อก contract; ตรวจด้วยบัญชีที่เพิ่งสร้างจาก UI |
| A3: ทะเบียนส่วนกลาง | โครงการ บ้าน ลูกค้า ค้นหา/แบ่งหน้า/แก้/เก็บเข้าคลัง และจัดการลิงก์ | โครงการต้องมี migration/backfill ก่อนทะเบียนบ้าน; งานลูกค้าและลิงก์ทำคู่กันได้หลัง A1 แต่รวมหลัง ownership tests ผ่าน |
| A4: ภาพรวมและการใช้งาน | dashboard จากข้อมูลจริง ประวัติการจัดการ navigation และ error/empty/loading | พัฒนา read-only คู่ A2/A3 ได้; ตัวเลข/ทางเชื่อมตรวจหลังข้อมูลและตัวกรองนิ่ง |
| A5: ตรวจรับส่วนเพิ่ม | แอดมินสร้างบัญชี/บ้าน → พนักงานใช้ workflow → ลูกค้ารับมอบ; โปรไฟล์/reset/archive/เพิกถอนลิงก์ | รวม A1–A4 แล้วให้ผู้ใช้ตรวจส่วนจัดการก่อนรวม final UAT |
| P6: ปิดงาน | regression เดิม+ส่วนเพิ่ม, backup/restore, clean setup, UAT/คู่มือ | ทำหลังตรวจรับส่วนเพิ่ม เพื่อไม่ตรวจส่งมอบซ้ำก่อน scope ใหม่เสร็จ |

ไม่กำหนดวันส่งหรือมอบหมายให้สมาชิกจริง เพราะยังไม่มีข้อมูลกำลังคนและ deadline รอบนี้ ผู้ดำเนินงานหลักรับผิดชอบ auth/schema/การรวมผลเพียงรายเดียว เพื่อเลี่ยงการแก้ฐานสิทธิ์พร้อมกัน

## DoR

1. ขอบเขตโมดูลและ matrix สิทธิ์ข้างต้นตกลงแล้ว; บัญชีแอดมินเฉพาะยืนยันแล้ว
2. ระบุช่องที่แก้ได้ก่อน/หลังเริ่ม QC ทำสัญญา ตรวจลูกค้า และส่งมอบ; กำหนดข้อห้าม archive/ย้ายลูกค้าเมื่อมีงานค้าง
3. ตรวจข้อมูลชื่อโครงการซ้ำ/สะกดต่างกันและเลขบ้านชนกันก่อน backfill ไม่รวมโครงการจากการคาดเดา
4. สำรองฐานและ private storage ก่อน migration; ทดลอง migration บน test DB ก่อน dev; รายการรอข้อมูลไม่ถือว่าผ่าน
5. ข้อมูลบัญชีแอดมินจริงต้องมาจากผู้ใช้ ไม่ดึงชื่อหัวหน้ากลุ่มรายงานมาให้สิทธิ์เอง บัญชี/ข้อมูลใน test fixture ต้องติดป้ายสมมติ
6. แยกรหัสความสามารถส่วนเพิ่ม เช่น EXT-ACC/EXT-ADM ออกจาก UC-01–18 และคงต้นฉบับ SA เดิม พร้อมบันทึกผลกระทบของส่วนเพิ่ม

## DoD

1. เปิดแอปแล้วแอดมินเพิ่มบัญชีพนักงานผ่านหน้าเว็บได้ พนักงานเข้าครั้งแรก เปลี่ยนรหัส และทำงานตามสิทธิ์ได้โดยไม่แก้ SQL เอง
2. หน้าบัญชีส่วนตัวบันทึก/reload ได้ ยืนยันรหัสเดิมถูกต้อง ข้อมูลผิดมีข้อความที่อ่านได้ และเปลี่ยนสิทธิ์ตนเองจาก browser ไม่สำเร็จ
3. ปิดบัญชี/เปลี่ยนสิทธิ์/รีเซ็ตรหัส/เพิกถอนลิงก์แล้ว session เดิมใช้ต่อไม่ได้ ประวัติงานเดิมยังอ้างอิงได้
4. แก้บ้าน/โครงการที่มีประวัติไม่ทำเอกสารหรืองานเดิมหาย ไม่ให้แอดมินกำหนดสถานะให้ข้ามการตรวจ/ยอมรับ/เซ็น
5. การเก็บเข้าคลังและการนำกลับมี guard, เหตุผล และประวัติ ไม่ลบข้อมูลที่ถูกอ้างอิงถาวรจากหน้าจอทั่วไป
6. ห้ามปิด/ลดสิทธิ์แอดมินคนสุดท้าย รวมกรณีทำพร้อมกัน และตรวจ authorization ที่ server ทุก endpoint
7. Dashboard ตรงกับรายการภายใต้ filter เดียวกัน; ค้นหา/เรียง/แบ่งหน้า/reload รักษาบริบท
8. ผ่าน HTTP/DB/browser/มือถือ/keyboard/contrast ทั้งส่วนเพิ่มและ regression ที่ได้รับผลกระทบ พร้อม actual evidence ก่อนให้ผู้ใช้ตรวจรับ
9. คู่มือเปิดระบบ/บัญชีแรก/reset/backup/restore และแผนเทียบกับ SA อัปเดตตรงโปรแกรมจริง

## ECC / ความเสี่ยง / การกู้คืน

| เหตุ | การตอบสนอง |
|---|---|
| privilege escalation หรืออ่าน/แก้ข้ามบ้าน | ปิดเฉพาะ endpoint ที่กระทบ เก็บกรณีทำซ้ำ แก้และทดสอบทุกเส้นทางที่ใช้ guard ร่วม |
| ปิดแอดมินคนสุดท้ายพร้อมกัน | transaction และ lock ตรวจจำนวนแอดมิน active ใหม่ก่อน commit ต้องเหลืออย่างน้อยหนึ่งคน |
| เปลี่ยนประเภทช่างขณะมีงานรับไว้ | ปฏิเสธการเปลี่ยน พร้อมรายการงานที่ต้องจัดการก่อน ไม่ทิ้งงานค้างหรือย้ายช่างเองเงียบ ๆ |
| ย้ายลูกค้าบ้านที่เริ่มตรวจแล้ว | ปฏิเสธและรักษาความสัมพันธ์เดิม ต้องออกแบบกรณีแก้ไขเฉพาะก่อนเปิดความสามารถนี้ |
| backfill โครงการชนกัน/ข้อมูลคลุมเครือ | หยุด migration ส่วนนั้น ส่งรายการจริงให้ผู้ใช้ตัดสิน ไม่รวมชื่อหรือเปลี่ยนเลขบ้านเอง |
| migration/commit ล้มเหลว | rollback ที่ทำได้ เก็บไฟล์ที่ผล commit ยังไม่แน่นอน ไม่เขียนทับ backup แล้วพิสูจน์ restore บน DB แยก |
| ลืมรหัสผ่าน | ใช้แอดมินรีเซ็ตพร้อมบังคับเปลี่ยนและเพิกถอน session เป็น baseline; ช่องทางส่งอีเมลต้องมีการเชื่อมต่อจริงก่อนอ้างว่าส่งแล้ว |
| กฎใหม่ทำให้ workflow เดิมเปลี่ยน | ทำ impact map UC/Q/SCR และปรับ acceptance/fixture ตาม requirement ที่เพิ่ม ไม่ลด assertion เพื่อให้ผ่าน |

ผลทดสอบ G2 เดิมเป็นหลักฐานของเวอร์ชันเดิม ส่วนเพิ่มมีผลจริงและ regression แยกใน evidence/management-*.json และ runtime-*.json โดยการรับความง่ายในการใช้งานยังรอผู้ใช้ตรวจ A5
